# 2. Jobとは何か

> **Job = 後で実行したい1つの仕事**

「今すぐやらなくてもいい」「今すぐやると遅くて待たせてしまう」処理を、**1つの単位として切り出したもの**が Job です。

## Jobになりやすい処理の例

| 例 | なぜ後回しにしたいか |
|---|---|
| メール送信 | SMTPサーバーの応答が遅い / 失敗したら再送したい |
| 画像リサイズ | CPUを使う。数秒かかることがある |
| CSV生成 | 件数が多いと数十秒〜数分かかる |
| 外部APIへのリクエスト | 相手のサーバーが遅い・落ちることがある |
| 大量データの集計 | 重い。ユーザーを待たせられない |
| 通知送信（Push / Slack等） | 失敗しても本体の処理は成功扱いにしたい |

## Jobのイメージ

```text
Job #001
「田中さんにメールを送る」

Job #002
「画像をリサイズする」

Job #003
「CSVを生成する」
```

Jobは実体としては「**何を・どのデータに対してやるか**」を持ったデータです。

```json
{
  "id": 1,
  "type": "send_email",
  "payload": { "user_id": 123, "template": "welcome" }
}
```

> 💡 **ポイント**
> Jobは「**実行するコードそのもの**」ではなく、「**何を実行してほしいかを表すデータ**」として運ばれます。
> 実行するコード本体は、Worker側が持っています。
> だからProducerとWorkerは**別プロセス・別サーバーでも成立**します。

> ⚠️ **注意**
> Jobのpayloadに巨大なデータ（画像本体など）を入れないのが定石です。
> **「S3のキー」「DBのID」だけを入れて、実体はWorkerが取りに行く**のが一般的な設計です。
