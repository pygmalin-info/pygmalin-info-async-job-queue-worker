# 11. トランザクション分離レベル

> ⚠️ **用語の訂正**
> 「コミットレベル」という言葉を耳にすることがありますが、**正式な用語ではありません**。
> 正しくは「**トランザクション分離レベル（Transaction Isolation Level）**」です。

## 何を決めるものなのか

> **複数のトランザクションが同時に動いたとき、お互いの変更をどのように見せるか**

これだけです。DB内部の実装（MVCCなど）に深入りしなくても、この観点だけ押さえれば実務では十分です。

```text
トランザクションA          トランザクションB
（データを更新中）    ←?→   （データを読んでいる）

Bには、Aの「まだCOMMITしていない変更」が見えるべき？
Bが2回同じ行を読んだとき、値が変わっていてもいい？
        ↑
    これを決めるのが「分離レベル」
```

## 4つの分離レベル

弱い順（速い順）に並べます。

| 分離レベル | ひとことで | 起きうる問題 |
|---|---|---|
| **READ UNCOMMITTED** | 他のトランザクションの**未確定の変更まで見える** | ダーティリード |
| **READ COMMITTED** | **COMMIT済みの変更だけ**見える | ノンリピータブルリード |
| **REPEATABLE READ** | トランザクション中、**同じ行を読めば毎回同じ値** | （ファントムリード） |
| **SERIALIZABLE** | **1つずつ順番に実行したのと同じ**結果になる | （ほぼ起きない。ただし遅い / 競合エラー） |

## 用語をざっくり理解する

**ダーティリード**：まだCOMMITされていない、消えるかもしれない値を読んでしまう

```text
A: BEGIN; UPDATE 残高 = 5000;   （まだCOMMITしていない）
B:                              SELECT 残高 → 5000 を読む  😱
A: ROLLBACK;                    （5000は幻だった）
```

**ノンリピータブルリード**：同じ行を2回読んだら、値が変わっている

```text
B: SELECT 残高 → 1000
A: UPDATE 残高 = 5000; COMMIT;
B: SELECT 残高 → 5000  😱（同じトランザクション内なのに変わった）
```

**ファントムリード**：同じ条件で2回検索したら、行が増えている／減っている

```text
B: SELECT COUNT(*) WHERE status='pending' → 3件
A: INSERT INTO jobs ...; COMMIT;
B: SELECT COUNT(*) WHERE status='pending' → 4件  😱
```

## どのレベルで何が防げるか

| 分離レベル | ダーティリード | ノンリピータブルリード | ファントムリード |
|---|---|---|---|
| READ UNCOMMITTED | ❌ 起きる | ❌ 起きる | ❌ 起きる |
| READ COMMITTED | ✅ 防ぐ | ❌ 起きる | ❌ 起きる |
| REPEATABLE READ | ✅ 防ぐ | ✅ 防ぐ | ❌ 起きる※ |
| SERIALIZABLE | ✅ 防ぐ | ✅ 防ぐ | ✅ 防ぐ |

※ MySQL(InnoDB) の REPEATABLE READ は、実装上ファントムリードもほぼ防ぎます。**DBによって挙動が違う**点に注意してください。

## 実務でのデフォルト

| DB | デフォルト分離レベル |
|---|---|
| PostgreSQL | READ COMMITTED |
| MySQL (InnoDB) | REPEATABLE READ |
| Oracle | READ COMMITTED |
| SQL Server | READ COMMITTED |

> 💡 **ポイント**
> **分離レベルを上げるほど安全になりますが、その分だけ遅く / 競合しやすくなります**。
> ほとんどのアプリはデフォルトのままで問題ありません。
> 「なんとなく不安だからSERIALIZABLEにする」は、**性能を大きく落とすだけで、狙った問題が解決しないこともあります**（→ 次章）。
